# Milestone 7 Prompt: Frontend Baseline

You are a senior UI/UX designer and senior frontend engineer at a top Silicon Valley company. You have deep expertise in React, modern CSS, component architecture, and data-dense admin interfaces.

## Project Context

You are building a baseline admin frontend for CudaAwareDistributedScheduler — a CUDA-aware overlay job scheduler with a FastAPI control plane, Redis job queue, and Postgres state store. The backend is already running. Your job is to build the frontend from scratch.

## Tech Stack

- React + Vite
- TypeScript
- Tailwind CSS for styling (utility-first, dark-mode-first)
- react-router-dom for routing
- No component library — build lightweight components directly with Tailwind

## Design Direction

Take strong inspiration from PostHog's admin/product UI:

1. Clean, modern aesthetic with a dark-mode-first design
2. Sidebar navigation with clear section hierarchy
3. Cards and panels for data display — generous whitespace, clear visual grouping
4. Subtle borders and surface elevation instead of heavy shadows
5. Monospace or semi-monospace typography for technical data (job IDs, node IDs, timestamps, exit codes)
6. Status indicators using color-coded badges/pills (e.g., green for DONE, amber for RUNNING, red for FAILED, gray for QUEUED)
7. Data tables that feel light and scannable, not heavy or enterprise-y
8. Muted color palette with selective accent colors for interactive elements and status
9. Smooth but minimal transitions — nothing flashy
10. The overall feel should be: "engineer built this for engineers" — information-dense but not cluttered

## Pages to Build

### 1. Dashboard (`/`)

- Show control-plane health status (green/red indicator from `GET /health`)
- Show readiness status (from `GET /ready` — includes postgres and redis status)
- Job summary cards showing counts by state: QUEUED, PLACED, RUNNING, DONE, FAILED, CANCELLED (from `GET /api/jobs/summary`)
- Quick-links or navigation to Jobs and Nodes pages

### 2. Jobs (`/jobs`)

- Table of recent jobs from `GET /api/jobs`
- Columns: job_id, state (color-coded badge), node_id, exit_code, reason (truncated), enqueued timestamp
- Clicking a row expands or navigates to job detail showing full timestamps map (spec is not available from the current API — show only `JobStatus` fields)
- "Submit Test Job" button/panel that sends `POST /api/jobs` with a configurable command
  - Default: `{"job_id": "<auto-generated>", "image": "", "cmd": ["echo", "hello"]}`
  - Let the user edit the command before submitting
- Auto-refresh toggle: when enabled, polls `GET /api/jobs` every 3 seconds
- Show the API response status on submission (201 created vs 200 duplicate)

### 3. Nodes (`/nodes`)

- List of nodes from `GET /api/nodes`
- Each node displayed as a card or expandable row showing:
  - node_id
  - Last heartbeat (relative time, e.g., "12s ago")
  - GPU inventory: list of GPUs with name, total memory, utilization %, used memory, temperature
  - Agent health details
- Visual indicator for node freshness (green if heartbeat < 30s ago, yellow if < 120s, red/stale otherwise)

## Backend API Endpoints

Existing endpoints (already implemented):

- `GET /health` — returns `{"ok": true, "service": "control_plane"}`
- `GET /ready` — returns `{"ok": true, "postgres": {"ok": ...}, "redis": {"ok": ...}}`
- `GET /api/jobs/{job_id}` — returns `JobStatus` object (state, node_id, gpu_ids, timestamps, exit_code, reason — does not include the original job spec)
- `POST /api/jobs` — accepts `JobSpec`, returns `{job_id, created, status}`
- `GET /api/nodes` — returns list of `NodeInfo` objects

New endpoints (will be added as part of this milestone):

- `GET /api/jobs` — returns a flat list of all jobs ordered by enqueue time descending, each shaped as `{job_id, state, node_id, gpu_ids, timestamps, exit_code, reason}` (note: the field is `state` not `status`, consistent with `JobStatus`)
- `GET /api/jobs/summary` — returns `{queued: N, placed: N, running: N, done: N, failed: N, cancelled: N}`

## CORS

CORS middleware is already enabled in the FastAPI app with `allow_origins=["*"]` (see `control_plane/app.py`). No additional CORS work is needed for local development. When tightening for production later, restrict origins to the frontend's actual URL.

## API Base URL

The FastAPI backend runs at `http://localhost:8000`. The Vite dev server runs at `http://localhost:5173`. Use a configurable API base URL (environment variable or config constant).

## File Structure

Place the frontend in a `frontend/` directory at the project root:

```
frontend/
  package.json
  vite.config.ts
  tsconfig.json
  tailwind.config.ts
  index.html
  src/
    main.tsx
    App.tsx
    api/           — API client functions
    components/    — shared components (StatusBadge, Card, Layout, Sidebar, etc.)
    pages/         — Dashboard, Jobs, Nodes
```

## Constraints

1. Keep it simple — this is a baseline admin UI, not a product. Avoid over-abstraction.
2. No state management library — React useState/useEffect and lifting state is sufficient at this scale.
3. No routing library heavier than react-router-dom.
4. Polling for data refresh (every 3 seconds when auto-refresh is on), not WebSockets.
5. The UI must be functional and useful, not just pretty. An engineer should be able to submit a job, watch it progress through states, and verify the system is healthy — all from the browser.
6. All API calls should handle loading, error, and empty states gracefully.
7. Use semantic HTML and accessible patterns where practical.
